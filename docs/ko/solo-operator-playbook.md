# 1인 개발자를 위한 운영 판단 플레이북

이 문서는 기존 암묵지를 실제 작업량·돈·운영 부담에 연결한 보강판이다. 새 운영 방식은 제안이며, 외부 자료와 가상 계산 결과를 개인의 성공 경험으로 기록하지 않는다.

## 기능 목록보다 먼저 결정할 것

현재 프로젝트 노트에 아래 내용을 한 장으로 정리한다. 별도 대시보드나 에이전트 팀을 새로 만들 필요는 없다.

```text
누구의 어떤 문제를 해결하는가:
현재 단계: 탐색 / 검증 / 개발 / 운영 / 일시중지
이번에 완성할 하나의 사용자 결과:
확인한 근거와 아직 모르는 가정:
이번 기간의 총시간과 운영에 필요한 시간:
추가 지출 한도와 사용자당 변동비:
이번 범위에서 하지 않을 것:
첫 사용자를 만날 경로와 첫 가치 경험:
검증할 결과와 지속·수정·중단 조건:
실패 시 되돌릴 방법과 외부 작업 승인:
현재 에이전트·수정 담당·선행 작업·다음 행동:
```

기본 제안은 한 번에 주요 성장 가설 하나, 공유 작업 폴더의 변경 담당 하나다. 장애 대응이 끼어들면 기존 작업을 어디에서 멈췄는지 남긴다. 이는 영구적인 개인 선호나 모든 프로젝트에 맞는 최적값이 아니다.

## 상황별 판단 10개

| 상황 | 실제로 적용할 판단 |
|---|---|
| 여러 앱을 동시에 키우고 싶다 | 이번에 알아야 할 결정 하나와 그 때문에 미루는 일을 명시한다. 종료한 프로젝트를 오래된 노트만 보고 재개하지 않는다. |
| 시간이 있으니 기능부터 만든다 | 지원·유지보수·배포/유입 활동·예비 시간을 빼고 개발 가능한 시간을 계산한다. 모르는 시간을 0으로 채우지 않는다. |
| 문의가 올 때마다 기능을 추가한다 | 고객 피해, 재현 여부, 우회 방법, 대상 고객과의 관련성을 구분한다. 데이터 손실·무단 과금·핵심 기능 장애는 일반 문의 묶음 처리보다 우선한다. |
| 반복 작업은 전부 자동화하고 싶다 | 불필요한 단계 제거와 기존 도구를 먼저 검토한다. 제작 시간뿐 아니라 유지 시간, 실제 반복 횟수, 실패 처리 부담을 함께 계산한다. |
| 매출이 나니 사업이 성립한다고 본다 | 고정비 충당과 운영자 소득 목표를 분리한다. 목표 고객 수에서 감당해야 할 고객 지원도 다시 계산한다. |
| 기능은 완성했지만 첫 사용자가 없다 | 대상 고객·한 가지 유입 경로·실제 변경에 근거한 문구·첫 가치 경험을 같이 준비한다. 초안 작성과 공개 게시를 구분한다. |
| 장애 중 원인 분석만 계속한다 | 영향 파악 후 승인된 되돌릴 수 있는 완화책을 먼저 검토한다. 실제 사용자 흐름 복구와 원인 해결은 별도로 기록한다. |
| 백업 성공 표시가 있으니 안심한다 | 격리된 대상에 복원해 소요 시간·데이터 손실 범위·앱과 데이터 일관성을 확인한다. 데이터베이스 외 파일 저장소 등도 확인 대상이다. |
| 운영 부담 때문에 서비스를 접고 싶다 | 유료 이용자 권리, 공지, 내보내기, 데이터 보관 의무, 반복 비용, 재개 조건을 먼저 정리한다. 성장 활동 중지와 데이터 삭제는 다르다. |
| 커밋·푸시를 요청받았다 | 검토한 파일만 스테이징하고 개인 기록·비밀정보·무관한 생성물을 제외한다. 푸시 후 원격 커밋까지 확인하되 배포 성공으로 확대하지 않는다. |

반복 운영 작업과 자동화의 비용·효과 비교는 [Google SRE 운영 지침](https://sre.google/workbook/eliminating-toil/)을 참고했다. 장애 시 피해 완화 우선순위는 [사고 대응 지침](https://sre.google/workbook/incident-response/), 복구 시간과 허용 데이터 손실 범위는 [재해 복구 계획 지침](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)을 참고했다. 대규모 조직의 비율·인력 구성·복구 목표를 1인 사업에 그대로 적용하지 않았다.

## 읽기 전용 계산기

저장소 루트에서 가상 예제를 실행한다.

```bash
python3 toris-solo-founder/scripts/assess_constraints.py toris-solo-founder/examples/solo-project.json
```

실제 사업 데이터를 사용할 때는 예제의 필드 구조에 맞는 **별도 비공개 입력 파일**을 지정한다. `input_class`는 `user_supplied`로 표시하고 모르는 숫자는 `null`로 둔다. 이 표시는 직접 검증된 수치라는 뜻이 아니다. 개인 입력을 공유 저장소에 커밋하지 않는다.

계산기는 입력 파일 또는 표준 입력만 읽고 JSON을 출력한다. 네트워크 호출·파일 저장·요금제 변경·자동화 설치를 하지 않는다. 문법이 잘못된 JSON, 중복 키, 불리언을 숫자로 사용한 값, 음수·무한대·잘못된 단위 표기는 오류로 처리한다.

### 단위와 이중 계산 주의

모든 반복 값은 하나의 기간(`week`, `month`, `year`)을 사용한다. 금액은 하나의 통화 표기만 사용하며 환율 변환이나 통화의 유효성을 검증하지 않는다. 주간 시간을 월 매출과 섞거나 연간 결제액을 그대로 월 수입으로 넣지 않는다.

`net_receipts_per_payer`는 이미 환불·결제/스토어 수수료를 제외한 기간당 사용자 수입이다. 같은 수수료를 `variable_cost_per_payer`에서 다시 빼지 않는다. 운영자 소득 목표는 `owner_pay_target`이며 같은 금액을 고정비에 중복 포함하지 않는다. 시간 항목도 겹치지 않아야 한다.

### 가상 예제로 계산되는 값

| 항목 | 예제 결과 | 의미 |
|---|---:|---|
| 총 가용 시간 | 40시간/월 | 실제 Toris의 일정이 아닌 가정 |
| 운영 약속을 뺀 개발 여력 | 12시간/월 | 16시간짜리 기능은 그대로 배정할 수 없음 |
| 사용자당 기여금액 | 7,000원 | 순수입 10,000원에서 변동비 3,000원 차감 |
| 고정비를 충당하는 고객 수 | 15명 | 고정비 100,000원을 충당하는 선형 계산 |
| 운영자 소득 목표까지 충당하는 고객 수 | 300명 | 같은 고정비와 추가 소득 목표 2,000,000원 기준 |
| 현재 가정한 12명에서 고정비 차감 후 금액 | -16,000원 | 실제 손익이나 세무 계산이 아님 |
| 자동화 시간 회수 기간 | 3개 기간 | 제작 6시간, 기간당 순절약 2시간 기준 |

판매량·이탈·세금·현금 유입 시차·지원 업무 증가·가격 변동은 자동 추정하지 않는다. 기여금액이 0 이하라면 의미 있는 양의 기여 기반 손익분기 고객 수를 만들지 않는다. 입력이 부족한 부분은 미확인으로 남기되 독립적으로 계산 가능한 부분은 출력한다.

## 하루와 주간 운영에 적용

작업 시작 때 현재 고객 피해나 과금 이상이 있는지 먼저 확인하고, 없으면 현재 성장 가설의 다음 행동 하나를 선택한다. 완료할 때 변경·검증·미검증·다음 행동만 짧게 남긴다. 매번 새 관리 문서를 만들지 말고 기존 프로젝트 노트를 활용한다.

사용자가 정한 검토 시점에는 실제 배포 결과, 고객 신호, 운영 비용, 지원 시간, 바뀐 가정, 지속·수정·중단 결정을 확인한다. ‘매주 검토’라는 문서가 일정이나 자동 알림을 실제 생성한 것은 아니다.

```text
이 저장소의 toris-solo-founder/SKILL.md와
 toris-solo-founder/references/solo-operator-playbook.md를 함께 읽어.
현재 프로젝트에서 혼자 감당할 수 있는 작업량, 운영 비용,
고객 지원 부담과 다음 사용자 결과를 먼저 정리해.
수치가 없으면 만들지 말고 미확인으로 남겨.
현재 에이전트를 유지하고 승인된 범위만 실행해.
실제 결과와 계산 가정·제안·미검증을 구분해서 한국어로 보고해.
```

이번 작업에서 기존 `SKILL.md` 본문 수정은 도구 보안 검사로 차단되어 변경하지 않았다. 대신 패키지 README와 5개 언어 가이드에 명시적인 진입점을 추가했다. 새 자료가 자동으로 로딩되거나 다른 에이전트에 설치됐다고 주장하지 않는다.
