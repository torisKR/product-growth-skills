# Toris solo founder

Turn a request into a bounded business outcome, verified local work, and a reusable lesson. Treat source evidence, historical preferences, and new recommendations as different things. This is an operating skill, not an always-on autonomous service.

## Quick start

1. Read the project's own instructions and [execution defaults](../shared-references/execution-defaults.md). Preserve existing changes and the user's selected agent. Do not install tools, switch providers, or publish as a side effect.
2. Identify the customer, problem, intended outcome, scope, cost ceiling, acceptance evidence, and next decision. Record unknowns rather than inventing them.
3. Read only the relevant reference below. Use the private operator dossier only in the owner's authorized personal context; never assume it ships with this skill.
4. Carry out the requested mode: execute safe in-scope local work, review without changes, or plan without implementation.
5. Report what changed, what was verified, what remains unverified, and the next decision. Harvest only supported lessons.

## Operating boundaries

- The user remains the decision-maker. A proposed experiment is not an approved budget, subscription, purchase, or public campaign.
- Default to one writer for a shared checkout. Parallel writing needs explicit ownership and isolated checkouts/worktrees; overlapping paths or unresolved dependencies stay serial. Do not require multi-agent operation when the user selected one agent.
- A provider response, an assistant's completion message, a local test, a CI run, and a live release prove different stages.
- A historical success is not current production evidence. An installed third-party skill is not the owner's personal experience.
- Never silently equate OpenCode with OpenCodex, or an OpenCodex provider with the application that launched the task.
- Read permissions do not authorize credential copying. Do not ingest authentication files, private keys, customer records, or full conversation databases into this repository.
- No background automation is created by these documents. Scheduling, accounts, permissions, global agent configuration, deployment, and external messages require their own explicit scope and supported tools.
- Verify changing prices, store rules, laws, framework behavior, and service policies against current primary sources when an actual task depends on them.

## Evidence contract

Use these labels consistently:

- **Observed:** inspected artifact or output, with its date and source type. Reading a curated historical note only proves what that note records.
- **Historical directive:** a dated user preference or decision; check scope and later changes before applying it.
- **Proposed:** a new operating method or experiment, not a proven personal result.
- **Unknown / not inspected:** absent evidence, blocked access, or a check that was not run.

Retain the distinction in final deliverables. Do not flatten uncertainty while summarizing.

## Definition of done

- Scope and acceptance evidence are explicit; unrelated work is preserved.
- All changed files are identified and the applicable local checks have actually run.
- Implementation, local validation, interaction testing, CI, deployment, public availability, and business results are reported separately where relevant.
- Costs and external actions remain within explicit authorization.
- New knowledge includes the situation, decision, evidence, limitation, and reuse trigger, or remains a candidate if unproven.
- The handoff is in the user's language. It never claims automatic installation, cross-agent execution, revenue, or production success without direct evidence.
